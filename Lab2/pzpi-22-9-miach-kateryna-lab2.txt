2.1 Мета роботи
На лабораторній роботі №2 потрібно розробити серверну / back-end частину програмної системи.
2.2 Хід роботи
1. Програмна система "HoneyTrack" використовує клієнт-серверну архітектуру. Вона складається з веб-клієнта (React.js), мобільного клієнта (Kotlin), IoT-клієнта (ESP32) та центральної серверної частини. Архітектура серверної частини побудована на Node.js з фреймворком Express.js та ORM Sequelize для роботи з БД SQLite. Вона має шарову структуру:
● Роутинг (routes/): визначає API ендпоінти (наприклад, /api/honey-batches).
● Контролери (controllers/): обробляють HTTP-запити, викликають сервіси.
● Сервіси (services/): містять бізнес-логіку та взаємодіють з моделями.
● Моделі (models/): представлення таблиць БД через Sequelize ORM.
● Middleware: для аутентифікації (JWT), обробки JSON, CORS, обробки помилок.

2. Основна обробка даних включає:
● Порівняння: значення з IoT-датчиків (температура, вологість) порівнюються з пороговими значеннями, встановленими користувачем (value < min_threshold OR value > max_threshold), для генерації сповіщень.
● Фільтрація та сортування: дані (наприклад, партії меду, показання датчиків) фільтруються за критеріями (дата, ID користувача, тип значення) та сортуються (наприклад, за датою, назвою) при виконанні запитів до БД через Sequelize.
● Базові арифметичні операції: можуть використовуватися при агрегації даних (наприклад, підрахунок кількості, хоча складні розрахунки наразі не реалізовані).
● Робота з датами/часом: для запису часових міток (createdAt, updatedAt, timestamp для показань) та фільтрації за періодами.
Складних математичних моделей або статистичного аналізу на даному етапі не використовується.
3. ER-модель системи "HoneyTrack" включає сутності: Users, StorageLocations, Sensors, HoneyBatches, SensorReadings, NotificationSettings, Alerts. Зв'язки переважно "один-до-багатьох" (наприклад, User має багато HoneyBatches). Структура БД реалізована в SQLite.
Приклад SQL DDL для створення таблиці Users:
CREATE TABLE IF NOT EXISTS Users (
user_id INTEGER PRIMARY KEY AUTOINCREMENT,
username TEXT NOT NULL UNIQUE,
password_hash TEXT NOT NULL,
email TEXT UNIQUE,
created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
updated_at DATETIME
);

4. Використовується REST API на основі HTTP з JSON для обміну даними. Аутентифікація здійснюється через JWT (Bearer token).
Базовий URL: /api
Приклад ендпоінтів для ресурсу "Партії меду" (/honey-batches):
POST /: Створити нову партію (тіло: JSON з даними партії).
GET /: Отримати список партій поточного користувача.
GET /:batchId: Отримати партію за ID.
PUT /:batchId: Оновити партію (тіло: JSON з даними для оновлення).
DELETE /:batchId: Видалити партію.

Платформа: Node.js

Аутентифікація: JWT (jsonwebtoken, bcryptjs)

6. Серверна частина наразі не реалізує глибоку інтернаціоналізацію (i18n). Системні повідомлення API (успіх, помилки) повертаються англійською мовою. Основна логіка локалізації інтерфейсу покладається на клієнтські додатки (веб та мобільний), які можуть використовувати файли ресурсів для перекладу на основі кодів помилок або стандартизованих повідомлень від API.
7. Серверна частина реалізована на Node.js/Express.js з використанням Sequelize ORM.
Моделі (models/): визначають структуру даних та зв'язки.
// Приклад: models/honeyBatch.model.js
module.exports = (sequelize, DataTypes) => {
const HoneyBatch = sequelize.define('HoneyBatch', { /* ... поля ... */ }, { /* опції */ });
HoneyBatch.associate = (models) => {
HoneyBatch.belongsTo(models.User, { foreignKey: 'user_id' });
};
return HoneyBatch;
};
Сервіси (services/): інкапсулюють бізнес-логіку та взаємодію з моделями.
// Приклад: services/honeyBatchService.js
const { HoneyBatch } = require('../models');
async function createHoneyBatch(userId, data) {
return HoneyBatch.create({ ...data, user_id: userId });
}
Контролери (controllers/): обробляють HTTP-запити, викликають сервіси.
// Приклад: controllers/honeyBatch.controller.js
const service = require('../services/honeyBatchService');
exports.create = async (req, res, next) => {
try {
const batch = await service.createHoneyBatch(req.user.user_id, req.body);
res.status(201).json(batch);
} catch (error) { next(error); }
};
Роути (routes/): визначають ендпоінти API.
// Приклад: routes/honeyBatch.routes.js
const router = require('express').Router();
const controller = require('../controllers/honeyBatch.controller');
const auth = require('../middleware/auth.middleware');
router.post('/', auth, controller.create);

Middleware: для аутентифікації (JWT), обробки помилок.
8. Функціональне тестування REST API серверної частини проводилося за допомогою інструменту Postman і включало наступні етапи:
1) Тестування аутентифікації: перевірка реєстрації (POST /api/auth/register) та логіну (POST /api/auth/login), отримання JWT.
2) Тестування CRUD-операцій для кожного ресурсу (наприклад, /api/honey-batches):
3) Створення (POST) з валідним токеном та даними.
4) Отримання списку (GET) та одного запису за ID (GET /:id).
5) Оновлення (PUT /:id).
6) Видалення (DELETE /:id).
7) Перевірка захисту ендпоінтів: спроба доступу до захищених ресурсів без токена або з невалідним токеном (очікується статус 401).
8) Перевірка валідації даних: надсилання запитів з некоректними або відсутніми даними.
9) Перевірка авторизації: переконання, що користувач має доступ лише до своїх ресурсів.

2.3 Висновки
В ході лабораторної роботи було успішно розроблено та протестовано серверну частину програмної системи "HoneyTrack". Спроектовано багатошарову архітектуру на Node.js, Express.js та Sequelize, що забезпечує взаємодію з базою даних SQLite. Реалізовано моделі даних, сервісний шар для бізнес-логіки та REST API з JWT-аутентифікацією для управління користувачами, запасами меду та даними з IoT-датчиків. Функціональне тестування за допомогою Postman підтвердило працездатність основних CRUD-операцій та захисту API. Розроблені UML діаграми (прецедентів, ER-модель, розгортання, компонентів) візуалізують прийняті архітектурні та проектні рішення.
2.4 Контрольні запитання
1) За якою програмною архітектурою побудована серверна частина програмної системи? Серверна частина програмної системи "HoneyTrack" побудована за багатошаровою архітектурою. Вона включає наступні логічні шари: шар роутингу (реалізований на Express.js), шар контролерів, шар сервісів (де зосереджена бізнес-логіка) та шар доступу до даних (реалізований за допомогою ORM Sequelize та моделей даних).
2) Які програмні технології та компоненти використовуються у серверній частині програмної системи? У серверній частині використовуються наступні програмні технології та компоненти: платформа Node.js, веб-фреймворк Express.js, база даних SQLite, ORM Sequelize, JWT (з бібліотеками jsonwebtoken та bcryptjs) для реалізації аутентифікації, а також допоміжні модулі, такі як cors для налаштування Cross-Origin Resource Sharing та dotenv для управління змінними середовища.

3) Яка бізнес логіка буде реалізована у серверній частині системи? Бізнес-логіка, реалізована у серверній частині системи, охоплює управління обліковими записами користувачів, включаючи їх реєстрацію та автентифікацію; облік та управління запасами меду, що дозволяє додавати, переглядати, редагувати та видаляти інформацію про партії продукції; реєстрацію та управління IoT-датчиками; автоматичний збір та збереження показань температури та вологості, що надходять від цих датчиків; а також функціонування системи сповіщень, яка інформує користувачів про вихід умов зберігання за попередньо встановлені ними межі.
4) Які ефективні математичні методи обробки користувацьких даних будуть реалізовані у серверній частині системи? Ефективні математичні методи обробки користувацьких даних, реалізовані у серверній частині, на даному етапі зводяться до операцій порівняння поточних значень параметрів (температура, вологість) із заданими користувачем пороговими значеннями для активації системи сповіщень. Також застосовуються стандартні операції фільтрації та сортування даних при формуванні відповідей на запити клієнтів через можливості ORM Sequelize.
5) Яка СУБД буде використовуватися для зберігання та обробки даних? Для зберігання та обробки даних у програмній системі використовується файлова реляційна система управління базами даних (СУБД) SQLite.
6) Які сутності представлені у БД та які звʼязки між ними? У базі даних представлені такі основні сутності: Users (користувачі), StorageLocations (місця зберігання), Sensors (датчики), HoneyBatches (партії меду), SensorReadings (показання датчиків), NotificationSettings (налаштування сповіщень) та Alerts (сповіщення). Зв'язки між цими сутностями переважно типу "один-до-багатьох", наприклад, один користувач може мати багато партій меду або датчиків.
7) Яку структуру має БД? База даних має реляційну структуру, що складається з набору взаємопов'язаних таблиць. Кожна таблиця містить стовпці з визначеними типами даних, первинні ключі для унікальної ідентифікації записів та зовнішні ключі для забезпечення зв'язків між таблицями та підтримки цілісності даних.
8) Які актори та які варіанти використання представлені на діаграмі використання (прецедентів) серверної частини програмної системи? На діаграмі прецедентів серверної частини програмної системи визначено два
10
основних актори: "Користувач (Пасічник)" та "IoT-пристрій". Для "Користувача" передбачені варіанти використання, такі як реєстрація, авторизація, управління партіями меду, перегляд даних з датчиків та налаштування сповіщень. "IoT-пристрій" має основний варіант використання – "Надіслати дані вимірювань".
9) Як буде здійснюватися захист персональних даних користувачів? Захист персональних даних користувачів забезпечується кількома методами: паролі користувачів гешуються за допомогою алгоритму bcryptjs перед збереженням; доступ до API захищений за допомогою JWT-аутентифікації; реалізована авторизація, що гарантує доступ користувачів лише до їхніх власних даних; а при розгортанні системи передбачається використання протоколу HTTPS для шифрування даних під час передачі.
10) Як у програмній системі забезпечуватиметься інтернаціоналізація? Інтернаціоналізація на серверній частині програмної системи на даному етапі реалізована обмежено: системні повідомлення API, такі як відповіді про успіх або помилки, повертаються переважно англійською мовою. Основна відповідальність за локалізацію інтерфейсу користувача покладається на клієнтські додатки (веб та мобільний).
11) Яка буде реалізована функціональність для адміністрування системи? Функціональність для адміністрування системи в поточній версії є базовою і включає можливість прямого доступу до бази даних SQLite для управління даними з боку розробника або адміністратора, а також моніторинг роботи серверної частини через аналіз консольних логів.
12) Як будуть створюватися резервні копії користувацьких даних та налаштувань системи? Резервні копії користувацьких даних та налаштувань системи будуть створюватися шляхом регулярного копіювання файлу бази даних SQLite (honeytrack.db) у визначене безпечне місце зберігання.
13) Як відновлюватимуться налаштування системи та користувацькі дані з резервних копій? Відновлення налаштувань системи та користувацьких даних з резервних копій здійснюватиметься шляхом заміни поточного файлу бази даних honeytrack.db на відповідний файл, збережений раніше як резервна копія.
